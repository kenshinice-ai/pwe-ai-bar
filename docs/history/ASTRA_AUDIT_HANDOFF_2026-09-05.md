## 4. 问题、建议和验收标准

### 01 · P0 · hook 安装可能覆盖已有配置

**位置**：`Providers/HookProvider.swift:78`，重点是以空字典开始、解析失败后仍继续写入的路径。

**触发**：已有 `~/.claude/settings.json` 存在，但内容无法解析。当前实现把它当作空配置继续安装，并返回成功。读取失败也没有与文件不存在明确区分。

**隔离复现**：写入不完整 JSON `{"existingSetting": true,`，安装返回 `true`，原内容未保留。没有操作用户真实文件。

**建议**：区分不存在、读取失败、解析失败及结构不支持；只有不存在时才允许从空配置建立。有效配置采用保留其他字段的合并写入，修改前备份。脚本复制及权限设置失败也应返回真实结果；安装状态应验证所需 hooks 和脚本，而非仅搜索字符串。

**验收**：

- 无文件时可以创建；有效文件中无关配置和已有 hooks 保留。
- 损坏或不可读文件安装失败，原字节不变。
- 重复安装不产生重复项；备份可恢复。
- 含空格和 shell 特殊字符的脚本路径正确引用。
- 复制脚本失败时不显示“已安装”。

### 02 · P1 · Codex 额度漏读、时间错误及过期误报

**位置**：`Providers/CodexProvider.swift:33`、`:38`、`:112`、`:145`。

**问题**：

1. 每个文件只取最后一个匹配行；末尾是 `premium` 时，同文件更早的 `codex` 主额度被忽略。
2. `observedAt` 使用文件修改时间，并非额度事件自身时间；无关内容追加会让旧额度显得刚更新。
3. 旧日志超过 `resets_at` 就直接生成 `percent: 0`，默认界面显示“剩余 100%”，但没有新证据确认实际恢复。

**隔离复现**：同文件先主额度后附加额度，主额度行数为 0；2020 年时间戳的记录被标记为 0 秒前读到；已过重置时间的记录显示剩余 100%。

**建议**：在受限扫描范围内，按 `limit_id` 分别归约最新有效事件，以事件时间跨文件比较；明确旧格式兼容和缺失时间的降级策略。到点只表示“预计已重置，等待新读数确认”，不能直接生成实测零用量。过期/推断数据不能触发“已确认恢复”通知。

**验收**：

- 同文件内交错主额度、附加额度、无关记录，仍能读到正确主额度。
- 更新文件 mtime 不改变额度观测时间。
- 无效尾行不会遮蔽此前有效记录。
- 重置时间已过且没有新观测时，显示待确认，不显示实测剩余 100%。
- 仍保持有界读取；若扫描范围不足，明确数据不可得。

### 03 · P1 · 事件并发丢失与慢轮询漏提醒

**位置**：`hooks/pwe-ai-bar-hook.sh:39`；资源副本 `Sources/PWEAIBar/Resources/pwe-ai-bar-hook.sh`；`Core/Store.swift:32`、`:77`、`:93`；`Core/RuleEngine.swift:133`。

**问题**：hook 通过读取旧日志、写共用 `.tmp`、rename 更新最近事件，并没有保护完整读改写事务。多个会话同时写入时会互相覆盖或损坏文件。事件又与额度刷新共用循环；空闲轮询可降至 5 或 15 分钟，规则却忽略超过 120 秒的事件。Claude 请求和日志扫描也在事件读取之前。

**隔离复现**：三轮各 20 个并发事件，有效保留数分别为 15、15、18；第二轮另有 2 条无效记录；所有脚本均返回 0。

**建议**：选择具有并发安全保证的事件写入方式，例如每事件独立文件，或有明确并发保证的追加方案；不要仅改成随机临时文件就声称解决覆盖问题。事件读取独立于远程额度请求和空闲慢轮询，可采用文件变化监听及低成本兜底。保持 hook 不联网、快速退出、不阻塞编码会话的原则。

**验收**：

- 在小于容量上限的情况下，20 个并发合成事件全部可读，无损坏、无意外覆盖。
- 空闲降频后产生新等待事件，仍能及时唤起处理；建议目标为 5 秒内。
- 模拟远程请求挂起，不阻塞本地事件提醒。
- 超过容量后的清理行为有明确规则，不删除未消费事件造成静默遗漏。
- 两份交付脚本保持一致，或改为单一来源后在构建时验证产物。

### 04 · P1 · 提醒状态提前删除与点击后重播

**位置**：`Core/RuleEngine.swift:113`、`:174`；`AppShell.swift` 的 `activate`；`App/PanelView.swift` 的 `eventRow`。

**问题**：待重置记录在检查目标窗口是否存在、是否恢复前就被删除。仅另一 provider 有数据时，也会丢失提醒机会。`clearAttention()` 则清空已见事件，点击“去看看”并不会证明用户已经回复，却让相同紧急事件再次通过去重。

**隔离复现**：预置已到点的 Claude 待重置记录，快照只有 Codex，待提醒记录变为 0；同一等待事件首次产生 1 条提醒，调用清除后再次产生 1 条提醒。

**建议**：区分事件接收、通知投递、用户查看和真实解决；点击打开应用不清空全局去重集合。待重置记录保留到新鲜数据确认恢复，或明确的过期清理条件满足。规则测试应可注入时间。

**验收**：

- 对应窗口缺失、网络失败或快照过期时，待重置记录保留。
- 新观测确认恢复后恰好通知一次；重启后仍能兑现待提醒记录。
- 打开应用或点击提醒后，相同事件不再次通知。
- 同会话的新等待事件可正常提醒；一个会话的处理不清除其他会话状态。
- 静默期与多个窗口同时恢复时，不会无意丢掉需要通知的事实。

### 05 · P1 · 分级来源与“用尽”语义不一致

**位置**：`Core/Model.swift:69`，以及 `Core/RuleEngine.swift` 的 `.hot` 提醒。

**问题**：文档和注释描述服务端分级优先，实际 `band` 使用 `max(server, local)`。`gradedBy` 没有决定取值来源；本地阈值达到 hot 就会被文案称为“用尽”。

**隔离复现**：构造服务端 `normal`、使用率 96%、`gradedBy: .server` 的窗口，结果为 `hot`。

**建议**：明确分级契约：可信服务端 severity 存在时按服务端分级；缺失时才用本地阈值。将“接近上限”与“确认耗尽”分开。缓存保存/恢复也要保留分级来源。

**验收**：服务端 normal/warning/critical、无 severity、缓存恢复、本地裸百分比均有测试；“用尽”文案必须有对应状态证据。若产品决定保留更保守的本地覆盖，应先明确改变契约，并同步文案和说明。

### 06 · P1 · 令牌保存失败与失效恢复不可见

**位置**：`Providers/Credentials.swift:56`；`Providers/ClaudeProvider.swift:225`、`:275`；`App/SettingsView.swift:74`。

**问题**：保存采用先删除再添加，添加失败可能丢失旧令牌。Provider 忽略存储返回值，设置页立即显示成功。401/403 没有独立恢复状态；429 仅按数字解析 `Retry-After`。界面把“未保存到期时间”表述为“不会过期”，证据不足。

**建议**：优先更新现有钥匙串条目，仅在不存在时新增；返回结构化结果，区分保存、验证中、有效、被拒绝和网络不可用。对无效凭据提供明确修复入口及合理重试节奏。支持合法 `Retry-After` 格式，不把长期令牌承诺为永不过期。

**验收**：使用模拟凭据存储和网络响应验证更新失败保留旧值、删除失败可见、UI 成功文案跟随真实结果、401/403 可恢复、429 遵守退避。未经授权不操作真实钥匙串。

### 08 · P2 · 设置语义、状态反馈和推送可验证性

**位置**：`Core/Notifier.swift:60`；`Core/Store.swift:90`；`Core/Prefs.swift:67`；`App/SettingsView.swift`。

**问题**：选择“菜单栏”仍会申请和发送系统通知；关闭 Claude 追踪后仍扫描其 transcript 和 hook 事件；开机启动失败被吞掉，开关继续显示开启。推送只发出请求，没有可见的成功/失败状态。

**建议**：明确设置是互斥提醒位置还是附加通道；明确“追踪”是只控制额度还是包括统计和事件，然后让命名与行为一致。开机启动读取系统实际状态，错误可恢复。推送增加 URL 校验、测试入口、最近结果和失败原因；若继续声明支持 ntfy/Bark，应分别验证实际请求协议，不能凭通用 POST 推断兼容。

**验收**：各选项与实际通知表面一致；追踪关闭后的处理行为符合界面描述；开机启动失败不显示已生效；推送测试用本地模拟端点，真实外部发送需用户授权。

### 09 · P2 · 上下文与等效成本口径

**位置**：`Providers/Transcript.swift:210`、`:219`；`Core/Pricing.swift:49`；`App/TrophyView.swift`。

**问题**：上下文容量根据模型名固定取值，没有实际会话容量来源。订阅同期摊销按活跃日数量计算，不能等同于包含闲置日的订阅成本。未知模型计价返回零，界面无法区分免费和未计价。

**建议**：上下文优先使用可靠元数据，缺失时明确标注估算。订阅金额及统计周期可配置，区分活跃天数与计费时间。未知价格显示未计价和覆盖率；价格数据记录来源与更新时间。若校正模型价格，应查证当时官方来源，不沿用记忆或猜测。

**验收**：稀疏活跃日不会被当成完整订阅周期；未知模型不显示为已确认零成本；上下文缺失或无效容量不产生伪精确读数。等效 API 成本始终与真实账单支出区分。

### 10 · P2 · 增量缓存与时区边界

**位置**：`Providers/Transcript.swift:110`、`:143`、`:197`。

**问题**：继续增量读取的判断主要是新文件大小大于等于旧解析偏移。等长或更长的重写、文件替换可能沿用旧 digest。历史日期分桶使用当前 GMT 偏移，跨夏令时或切换时区存在错位风险。

**建议**：增加足以区分追加和替换的文件身份/前缀校验。明确按事件当时本地日期或固定时区统计，并纳入缓存版本与失效策略。

**验收**：追加、尾部半行、截断、等长重写、更长重写、原路径文件替换后统计正确；夏令时和时区变更有用例。保留增量扫描性能，不因校验每次全读大文件。

### 11 · P2 · 读数时效、窗口适配和可访问性

**位置**：`App/PanelView.swift` 的 header、readingAge、footer；`App/SettingsView.swift`；`App/UsageChart.swift`。

**问题**：过期读数主要靠小圆点提示；底部“刚刚更新”是快照刷新时间，容易被理解为额度刚更新。设置页没有滚动容器；图标按钮、图表的辅助技术语义仍可完善。截图仅用于理解现有视觉方向。
